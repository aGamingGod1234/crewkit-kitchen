Make agent actions feel continuous

The selected AI agent remains the only author of gameplay decisions. Minecraft executes its bounded, preauthorized controls at tick speed and returns new facts when another decision is needed.

Audit complete Local handoff verified Live gameplay gain unproven

Goal and scope

Reduce avoidable idle time between movement, gathering, combat, and interaction steps. Preserve the selected model, goal revision, action provenance, factual observation barriers, and user stop/steer controls. The first change is in an isolated worktree based on merged main. The user's unrelated working-tree edits remain untouched. Nothing was installed or pushed.

What the code already provides

Tick-speed controls

control_sequence runs up to 64 agent-authored frames and observed-condition branches on the server, within a 2,000-tick budget. Source: ControlSequence.java:13–29,64–99.

Known action chains

sequence runs 2–8 exact actions in order, stops on failure, and returns one final post-action sample. Source: native-minecraft-tools.mjs:113–118; native-tool-runtime.mjs:491–503.

Reactive routines

runProgram executes bounded agent-authored ArenaScript. It waits for each physical result and a fresh observation before dependent continuation. Source: native-program-executor.mjs:99–149.

Warm sessions

Native agent sessions prewarm and a real event can adopt the active prewarm turn. The bridge admits action commands at the start of a server tick. Source: codex-service.mjs:569–619; MultiplexedServerBridge.java:424–467.

Evidence and limits

A historical 16-agent provider probe with simulated action bodies measured move-then-mine medians of roughly 4.8–5.2 seconds through separate calls versus 3.26–3.36 seconds through one sequence at low reasoning. It shows a model-call saving, not a current live Minecraft speedup (reports/native-tool-loop-three-runs-2026-08-22.json).

A September headless rehearsal recorded 18 physical actions totaling 23.3 seconds, while six provider turns totaled 104.6 seconds across an overlapping 107.2-second phase. Provider turns include tool waits, and API-only timing was absent, so these totals cannot isolate model inference (output/fast-pass-live-2-audit.json). Existing historical baseline comparisons also mix startup, provider, and gameplay; there is no defensible current human-speed baseline.

Internal program continuation now gets a fresh observation without rereading execution settings and unresolved notebook entries that only the model-facing observe result uses. Recommended steps

  1. Measure the gaps first. Record event-to-model request, model request-to-first tool, validation-to-bridge acceptance, acceptance-to-first physical progress, and completion-to-next authorized action. Label every idle interval. Use a fixed seed/profile and paired real Fabric runs; keep failures and cancellations.
  2. Make agent-authored continuation the normal path. Use sequence for known steps whose next target does not depend on a new fact; use runProgram for observed branches and repeated tasks; use control_sequence for precise tick-by-tick movement. Reuse saved agent-authored programs only after they read fresh facts. Avoid rapid startAction/actionStatus polling, which adds provider calls.
  3. Reduce observation work where measured. The server currently collects a full snapshot before computing a change delta. Test a versioned small-delta lane for routine updates and addressed events, retaining full snapshots for startup, recovery, and explicit inspections. A fact-only trigger may wake or steer the same selected model; it may never select an action.
  4. Profile navigation before tuning it. Complex routes can defer walking while bounded path search proceeds over ticks. Reuse terrain data only with proven chunk and mutation invalidation; do not alter motor acceleration or queue ordering on speculation.
  5. Test authority and gameplay together. Delay/fail the provider during a running routine: only already authorized steps may continue. Reject stale successor output after a goal change. Compare completed tasks, action errors, p50/p95 idle gaps, first movement, and server tick p95 across matched worlds, including 1, 8, and 16 agents. Aim for at least 30 paired samples per primary cell before treating p95 as stable.

Decisions and risks

Decision: keep one selected model as the sole source of target choices, branches, retries, pause/resume policy, and successor programs. Remove measured local overhead while preserving fresh facts and lifecycle fences. Future live comparisons need matched runs that actually exercise model-authored runProgram and separate model wait from local action handoff.

Risk: long open-loop movement can act on stale terrain or miss new danger. Bound each routine, specify agent-authored stop conditions, and return to the model when a choice needs new evidence. A newly encountered situation still incurs selected-model latency; continuous execution cannot make a fresh model decision instantaneous.
