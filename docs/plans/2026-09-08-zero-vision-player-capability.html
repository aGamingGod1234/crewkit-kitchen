Zero vision. Full player agency.

Give the AI a complete player interface.

Make Minecraft playable through factual text observations and reliable tools. The selected AI chooses what to do, including its reactions. The system supplies the information, hands, and memory to carry those decisions out.

01

A general player, on unfamiliar worlds

The target is an agent that can learn the situation, choose a strategy, and use ordinary player actions across seeds. Building, exploration, farming, trading, combat, travel, and full-game completion should all use the same systems.

Commit to equal capabilities across supported settings and measured success on unseen seeds. A universal win guarantee is impossible for unavailable providers, insufficient budgets, weaker decisions, or world rules that prevent completion. Those conditions must be reported honestly.

  • No images, screenshots, rendered frames, or vision models reach the agent. Text describes information a player could perceive, inspect, hear, or remember.
  • The selected provider, model, thinking level, and speed remain in force. Report requested and effective settings. Never silently switch to a stronger model.
  • Respect Survival, Creative, Adventure, and death-policy restrictions. Automatic respawn follows an explicit user setting or model-authorized policy. Equal tools do not erase game-mode rules or remove-on-death behavior.
  • Keep world seeds, unexplored structure locations, hidden mob state, operator commands, and evaluator-only data outside the agent interface.

For the later completion benchmark, record the chosen definition before each run. Proposed default: an agent-attributed dragon defeat with the corresponding advancement, followed by verified exit through the return portal. Reuse authoritative goal predicates and event evidence. This definition belongs to evaluation, never to execution policy.

02

The foundation exists. The contract is incomplete.

Raw input frames, exact-hand use, mining, placement, crafting, menus, short navigation, sequences, recovery, and authoritative completion already exist. Several August plans describe work that has since shipped. Extend these systems.

Four immediate blockers

  • ArenaScript cannot issue the complete control frame available to native agents.
  • Observations omit menu options, item variants, motion details, and sometimes whole candidate lists.
  • Menu accounting rejects changes outside two slots, including ingredients consumed by a valid result operation.
  • Exploration merges underground and surface locations, forgets other dimensions, and embeds destination preferences.

Two design conflicts

  • A live safety controller independently chooses swimming, escape, defense, and retreat. Goal-text wrappers also suggest progression steps.
  • Fast control and model ownership are split between runtimes. Native tools lack explicit action cancellation and reactive programs; ArenaScript has watchers but loses useful movement and menu facts.

Gemini planning is currently disabled because its adapter cannot enforce the required tool boundary. Treat it as unavailable until that boundary is supported.

Inspect source references and the reproduced failures.

03

One body contract. Every decision belongs to the AI.

1. ObserveFresh facts, detail queries, remembered places, and uncertainty.
2. AI decidesGoals, targets, routes, timing, resources, reactions, and retry policy.
3. Body executesBounded player inputs or a bounded program authored by that AI.
4. VerifyActual outcomes and changes return to the same AI for its next choice.

Mechanical code may follow an explicitly selected route, maintain an authorized aim constraint, validate reach, and release abandoned input. Choosing to flee, mine a shortcut, build a bridge, change targets, or pursue a structure requires a model decision or its previously authored rule.

Reuse the ArenaScript ownership, limits, and cancellation machinery. Add a small server-tick executor for a validated subset of model-authored input programs. The model can define short reactions before entering a risky situation. Each rule has observable conditions, explicit actions, expiry, priorities, and limits. Unknown situations yield to the model.

Example: the AI can authorize a timed shield response to a specified visible projectile condition. The runtime checks that condition and applies the authored input. It never invents a defense or escape plan. Keep lease expiry and stale-command rejection unconditional.

04

Build in verifiable steps

  1. Unify the contract and fix proven mismatches

    Add complete controls to program mode. Generate bindings and examples. Fix the invalid watcher example and inconsistent equipment fields. Define outcome levels and model authority before adding more helpers.

    Gate: equivalent native/program calls validate and dispatch identically; every shipped example executes; requested and effective settings are visible.

  2. Make facts fresh and actions accountable

    Add queryable details and explicit omissions. Introduce menu/stack revisions and action receipts. Fix consuming-menu accounting, held-use lease renewal, and successful-attempt claims that do not prove an effect. Keep strict conservation for storage transfers.

    Gate: real headless fixtures prove menu, input, and item effects through the production bridge, including stale state and partial execution.

  3. Give every model precise, interruptible control

    Add bounded input continuation, cancel/replace, and the common model-authored reaction contract. Then replace system-authored safety decisions and goal-specific exploration advice. Preserve mechanical input release and cancellation throughout the change.

    Gate: every physical choice traces to that model's call or authored program. Steering, stopping, death, and restart release old authority.

  4. Complete ordinary player interactions and travel

    Expand menu adapters, inventory operations, hit geometry, item details, and use lifecycles. Add persistent observed routes and movement-state feedback before extending swimming, climbing, vehicles, and flight. Return blockers when a route needs new resources or terrain changes.

    Gate: unfamiliar building, storage, workstation, traversal, combat, and text-interaction tasks work through the same controls.

  5. Preserve learning and prove transfer

    Persist model notes, observed places, and completed-action evidence. Reconcile uncertain actions before retrying. Extend the current headless runner with natural terrain, held-out seeds, supported settings, explicit budgets, and independent factual outcomes.

    Gate: long tasks survive context replacement and reconnects without duplicate mutations. Full-game attempts and unrelated tasks share the same tools and prompts.

Implementation ownership and dependencies

Use one integration owner for the shared contract, protocol, and dispatch changes. After that contract is fixed, assign separate owners to perception, menu transactions, input/reaction execution, and observed-world navigation. The integration owner alone edits shared dispatch and schema files when those branches meet.

Keep evaluation fixtures under a separate owner. Introduce one capability family and its real-server proof at a time. No map import, UI redesign, model training, provider substitution, or new gameplay policy is required for this work.

05

Measure capability before measuring wins

The existing natural-language game runner uses a prepared platform and supplied blocks. Simulator tests and mocked model programs prove useful contracts, but they cannot establish live player competence.

  1. Contract checks. Exercise every supported action and fact through both adapters. Test shipped examples, state references, limits, and truthful failure results.
  2. Real mechanics. Use a headless Minecraft server and the production bridge to verify movement, hit outcomes, resource consumption, inventory conservation, menus, portal transitions, and input cleanup. Scripted actions are appropriate at this stage.
  3. Real model composition. Give the selected model general tasks with varied coordinates and materials. Include sorting item variants, reading directions, building, farming, trading, crossing water, fighting moving targets, and returning to a remembered place.
  4. Held-out worlds and settings. Add fresh, unmodified generated worlds. Keep evaluation seeds hidden from the agent and separate development seeds from held-out seeds. Cover every supported profile at least once, then use pairwise operational coverage and targeted repeats after failures.
  5. Long runs. Attempt full-game completion alongside unrelated long tasks. Use the same general interfaces, preserve failures, and record independent outcome evidence.

Report the seed to the evaluator only, game rules, spawn conditions, requested/effective settings, limits, success counts, uncertainty, deaths, interventions, action failures, observation age, latency, and cost. Attribute failures to infrastructure, missing capability, missing information, execution, or model decisions. A win alone does not prove the system generalizes.

Acceptance criteria that protect the goal
  • Every supported configuration passes the common control/observation conformance suite. Availability and game-rule restrictions remain explicit.
  • Model inputs contain no image content or evaluator-only facts. Each live fact records its perception basis, age, and scope.
  • No physical action lacks model authorization, except neutral input release and other mechanical enforcement.
  • Every reported effect has factual evidence. A swing, item-use attempt, or projectile spawn cannot masquerade as a hit or task completion.
  • Every supported player-accessible detail omitted for size can be queried. Unavailable or unobserved facts remain explicitly unknown. Stale menus, stacks, targets, and world references fail safely without repeating an uncertain side effect.
  • Context replacement, reconnect, dimension transitions, and permitted death recovery preserve relevant knowledge while invalidating live control state.
  • Hold-out results use recorded budgets and all attempted runs. No seed-specific coordinates, win-route scripts, hidden stronger model, or completion-only helpers.
Risks and design decisions
  • Model latency: bounded model-authored programs keep already authorized actions responsive. Measure observation and reaction delay under concurrency. Do not pause the world or make the agent invulnerable to hide slow decisions.
  • Large observations: use focused queries, paging, and deltas. Increasing every payload limit would raise cost without guaranteeing useful detail.
  • Knowledge leaks: sounds, maps, hit geometry, and tooltips need explicit player-access rules. Full server state is not an acceptable substitute for vision.
  • Irreversible operations: record what happened and reconcile with live state after interruption. Generic rollback cannot undo every trade, craft, attack, or consumed item.
  • Version and provider drift: conformance is tied to the installed game and adapter versions. Mark unsupported combinations unavailable; do not disable enforcement to make a benchmark run.
  • Budgets: separate model thinking, body execution, and recovery time. Healthy progress may resume with the same selected model within explicit run limits.
06

Evidence behind the proposal

Nine read-only audits covered actions, perception, navigation, inventory, runtime ownership, settings, validation, prior designs, and adversarial review. No gameplay implementation, live model call, live-server operation, or world change was performed for this plan.

Checks performed and what they establish
  • Existing offline runs passed: 88 simulator/headless-runner/program tests; 83 native/runtime/program-authority tests; 15 exploration tests; 19 tool/schema tests. These are per-run counts with overlap.
  • Actual module probes showed that exploration merges cave and surface coordinates, forgets another dimension, retains an occupied cell as blocked, and ignores distant landmarks. A cue 96 blocks overhead was classified as in range because distance ignored height.
  • The actual parser rejected the prompt's watcher example because watcher handlers cannot call program.checkpoint. A valid native control frame was rejected by the program interface. Program facts dropped supplied movement, cooldown, and menu details.
  • The compiled transaction validator rejected an anvil-style before/after snapshot that moved the result and consumed input slots: TRANSACTION_CONFLICT: Unexpected slot 0 changed. This proves an accounting-contract mismatch. Each live menu path still needs a real Minecraft fixture.
  • Gemini's production adapter rejected planner creation with PROVIDER_UNAVAILABLE without starting a provider process. Other identified physics and timing issues are source-backed findings awaiting live fixtures.

Passing these tests does not establish successful survival on unseen seeds. It shows why stronger, focused integration evidence is needed.
