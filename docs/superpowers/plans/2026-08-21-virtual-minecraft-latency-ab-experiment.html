Virtual Minecraft latency A/B experiment

Build a deterministic 20 Hz Minecraft substitute, run the real agent stack against it, apply the hybrid-control optimizations to one isolated copy, and report the measured difference without confusing simulated results with live Minecraft evidence.

GoalMeasure baseline vs optimized
ExecutionLuna xhigh/max subagents
Provider modesInstant, replay, live
Loads1, 4, 8, 16 agents
For agentic workers. Use superpowers:subagent-driven-development. Read the approved spec first. Each task follows test-driven development, stays inside its assigned worktree and files, and receives specification review followed by code-quality review before integration.

Architecture and constraints

  • Spec: docs/superpowers/specs/2026-08-21-virtual-minecraft-latency-ab-experiment-design.md.
  • Freeze the current dirty working tree through a temporary Git index. Do not alter the user's index or working files.
  • Create .worktrees/latency-baseline and .worktrees/latency-optimized from the same snapshot.
  • Apply identical behavior-neutral instrumentation and simulator code to both copies. Apply runtime optimizations only to the optimized copy.
  • Use Java 25, Node 22 or newer, existing dependencies, protocol-v2, existing provider adapters, and the production ArenaScript path.
  • Never copy OAuth files, API keys, environment files, bridge secrets, runtime directories, or provider login stores.
  • Real-provider calls are bounded, opt-in, sequential across arms, redacted, and cleaned up after every result.
  • Report virtual tick performance as simulator evidence, never as Minecraft TPS.

Decisions and risks

  • Decision. Instrumentation is identical in both arms. Optimized-only instrumentation would invalidate the comparison.
  • Decision. Real-provider and replay results remain separate. Reduced provider-call count is reported as its own mechanism.
  • Risk. Live model nondeterminism can overwhelm local differences. Paired randomized trials and decision replay control this.
  • Risk. The simulator may reward behavior that does not transfer to Minecraft. Held-out seeds, production protocol use, Java controller tests, and explicit evidence limits reduce this risk.
  • Risk. Sixteen live provider sessions may exhaust provider or host limits. Strict concurrency, turn budgets, sequential arms, and cleanup checks contain the run.
  • Risk. The dirty source tree may be captured incorrectly. The temporary-index fixture and matching source manifests are the first blocking gate.
