Arena Agents · reliability design

Coordinator recovery without dead ends

Every supported failure gets a bounded fallback, a scheduled probe, and a tested route back to normal operation. Active goals remain owned by Minecraft and the selected AI profile never changes silently.

What is broken now

Restart exhaustion

Java stops restarting after the third unexpected coordinator exit.

Latched startup failures

One startup failure blocks every future retry for the Minecraft session.

Provider blocks the core

Codex initialization completes before the Minecraft bridge starts, so provider failure can take down reconciliation.

Fail-fast catalogs

One failed provider catalog can reject the entire model catalog and roster reconciliation.

The invariant

An unfinished active goal must always own one of the following:

  • queued or running provider work;
  • a Minecraft action or completion verification;
  • a pending fresh observation;
  • a recovery attempt with a deadline;
  • a named external blocker with periodic revalidation.

Infrastructure failures never turn active work into PAUSED, ERROR, or completed work. Only the player can ordinarily pause an agent.

Recovery state machine

STARTING -> AUTHENTICATING -> HEALTHY
    ^              |              |
    |              v              v
    +----------- BACKOFF <-- DEGRADED

BLOCKED_RETRYABLE -> BACKOFF
STOPPED

STOPPED is reserved for explicit shutdown or disabled autostart. Runtime failures keep retrying with capped backoff. Missing dependencies remain visible as BLOCKED_RETRYABLE and recover automatically when their state changes.

Process and runtime recovery

  1. Restart unexpected exits forever with delays of 1, 2, 5, 15, then at most 30 seconds.
  2. Replace a live process that misses its authentication deadline.
  3. Replace an authenticated process that remains disconnected beyond its reconnect window.
  4. Reset crash-loop history only after a stable authenticated interval.
  5. Stage and validate runtime generations before activation.
  6. Fall back to the last verified runtime if a candidate is corrupt, while repairing the preferred generation in the background.
  7. Keep bridge secrets and credentials outside runtime generations.

Subsystem isolation

Coordinator core

Configuration, persisted registry, Minecraft bridge, reconciliation, and work supervision start independently.

Providers

Start lazily for reconciled profiles. One failed provider cannot stop another provider or the bridge.

Catalogs

Use settled results. Failed sources contribute their last valid snapshot or deterministic fallback and refresh in the background.

Voice and diagnostics

Remain optional. Their failures use bounded fallbacks and cannot reject agent-control work.

Exact-profile guarantee

provider + model + reasoning effort + service tier

That profile remains immutable through every recovery. A failed provider session is fenced and replaced with a fresh session using the same profile. An unavailable profile enters BLOCKED_RETRYABLE until it returns or the player explicitly changes it.

Returning from fallback

Every fallback records its primary component, fallback mode, reason, generation, next probe time, failure count, and promotion condition.

  • Process promotion requires stable bridge authentication.
  • Provider promotion requires an accepted exact-profile operation.
  • Catalog promotion requires a complete valid snapshot.
  • Voice promotion requires a successful bounded synthesis or transcription.
  • Stale-generation success is discarded and cannot promote anything.

Fault-injection gate

Process

Crash before startup, during authentication, after authentication, and during active work. Exceed three crashes and still recover.

Runtime

Corrupt a candidate, remove and restore Node, occupy and release ports, and repeat reconciliation.

Providers

Fail startup, catalog, session creation, active turns, circuit probes, and exact-profile recovery independently.

Goals

Lose each boundary during multi-step work and prove no pause, duplicate action, false completion, or silent stall.

Optional systems

Terminate voice and diagnostics independently, restore them, and prove promotion without affecting control.

Soak

Repeat recoverable faults while proving bounded processes, timers, listeners, queues, and logs.

Acceptance criteria

  1. No transient or degraded failure creates a permanent latch.
  2. Every fallback has an automated, tested promotion path.
  3. The selected AI profile changes only through an explicit player operation.
  4. One component failure cannot stop unrelated healthy components.
  5. Every unfinished goal owns live, scheduled, or explicitly blocked recovery work.
  6. Restarts are idempotent and leave no duplicate actions or orphaned children.
  7. Status identifies the failing boundary and next recovery action.
  8. The full Java, coordinator, voice, protocol, simulator, headless, and fault-injection suites pass.

Limit

The mod cannot act while Minecraft or Windows is not running. After a JVM, GPU, or operating-system failure, the next Minecraft launch must clean stale processes, validate the runtime, reconcile persisted goals, and resume automatically.
