Arena Agents · approved design

Authoritative Minecraft goal verification

Minecraft decides when an agent has actually completed a request. The model chooses actions, but it cannot weaken the goal, prove its own success, or stop early.

Status: design approved Date: 26 August 2026 Next: implementation plan

Why this is needed

Sol treated starter crafting as completion of “beat the game,” stopped its goal supervisor, stood idle, and required new player messages to act again. The mod must own completion and persistent work.

Current failure

The model authors a weak condition, completes one subtask, reports success, and disables recovery.

Required behavior

The original objective stays active until Minecraft observes the exact requested result.

Core flow

Player request → goal compiler → frozen GoalSpec → agent actions → Minecraft verifier → continue or complete

  1. Known exact requests are recognized deterministically and begin immediately.
  2. Model-proposed verifier rules always require player confirmation.
  3. Ambiguous requests ask what counts as done.
  4. Minecraft freezes the accepted rule for the goal revision.
  5. The verifier evaluates authoritative server state after events and every 20 ticks.

Example: get an iron pickaxe

{
  "request": "Get an iron pickaxe",
  "status": "ACTIVE",
  "completion": {
    "type": "inventory_contains",
    "itemId": "minecraft:iron_pickaxe",
    "count": 1
  }
}

A stone pickaxe produces a factual rejection and the agent continues:

Goal not complete.
Required: minecraft:iron_pickaxe x1
Observed: minecraft:stone_pickaxe x1

The mod proactively completes the goal as soon as the inventory contains the iron pickaxe. It does not wait for the model to claim success.

Initial verifier rules

inventory_contains

Exact item ID and minimum count.

position_within

Coordinates, radius, and stable ticks.

advancement_granted

Exact per-agent advancement state.

entity_killed_by_agent

Agent-specific kill credit after goal creation.

block_matches

Exact block, position, and optional state.

operator_confirmed

Player confirmation for subjective outcomes.

Rules compose through all_of and any_of. Unknown rule types or fields fail closed.

Persistent lifecycle

AWAITING_CLARIFICATION → ACTIVE ↔ RECOVERING → SATISFIED

  • A provider turn ending never ends the goal.
  • A false finish request returns missing conditions and keeps working.
  • Death preserves the goal, evidence, revision, and queue.
  • Respawn automatically starts recovery and then resumes the objective.
  • Ambiguous new work asks Replace / Queue / Cancel while current work continues.

Liveness guarantee

An unfinished goal must own a deadline-bound provider turn, Minecraft action, intentional wait, recovery operation, or scheduled next decision.

  • No valid work lease for 2 seconds triggers a fresh observation and selected-model turn.
  • No factual world progress for 30 seconds triggers a stuck diagnosis and demands a different strategy.
  • Hung provider turns and lost timers expire. They cannot count as active forever.

A narrow body-safety controller may escape drowning, lava, fire, repeated damage, raise an equipped shield, and begin respawn recovery while model output is pending.

Acceptance checks

  1. A stone pickaxe cannot satisfy an iron-pickaxe goal.
  2. An iron pickaxe completes the goal immediately from live inventory state.
  3. False finish claims keep the same goal active and schedule another turn.
  4. Death and respawn preserve and resume the same goal revision.
  5. Another player killing the dragon cannot complete Sol’s dragon goal.
  6. Sol receiving dragon kill credit completes it.
  7. Active and queued goals survive save and reload.
  8. The captured Sol inactivity replay has no unexplained gap beyond the liveness lease.

Tests use real server-side Minecraft state, focused unit checks, headless Minecraft verification, and one live selected-model run.

Scope

This change covers goal compilation, authoritative verification, lifecycle persistence, liveness, death recovery, and limited body safety. It does not redesign agent selection, groups, voice transcription, or unrelated scenario completion.

Subjective goals never auto-complete without a player-approved measurable rule or direct player confirmation.
