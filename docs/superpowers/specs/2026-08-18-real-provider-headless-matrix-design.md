# Real-Provider Headless Matrix Runner

## Status

Approved direction: use the real provider adapters and a real headless Fabric server. The first implementation intentionally does not add a virtual Minecraft backend or scripted model profiles.

## Goal

Provide a repeatable developer command that sends real tasks to real Codex, Gemini/Antigravity, and Kimi provider sessions, executes their model-authored ArenaScript through the normal coordinator and Fabric mod path, and produces evidence-rich reports showing whether each task actually completed in headless Minecraft.

## Non-goals

- Do not replace the existing deterministic coordinator and fake-bridge tests.
- Do not add a fake or scripted provider mode to the developer command.
- Do not alter production provider selection, prompt contracts, action authorization, or lifecycle semantics for test convenience.
- Do not run against the user's normal `run/world` or an existing server.
- Do not make external provider calls part of `npm test`, Gradle `check`, or CI by default.
- Do not expose provider credentials, bridge secrets, or OAuth state in reports.

## Architecture

The feature has two layers:

1. A reusable Node.js runner owns matrix validation, scenario normalization, RCON commands, protocol/report capture, assertions, and result serialization.
2. A Windows PowerShell entrypoint owns process setup and teardown for the dedicated Fabric server and the real dynamic coordinator. It supplies the selected provider configuration and delegates all model work to the existing provider services.

The running data path remains the production path:

```text
scenario matrix
    -> headless runner
    -> RCON /codex summon + /codex start
    -> Java Fabric mod and authenticated protocol-v2 bridge
    -> DynamicCoordinator
    -> AgentPlanner
    -> real Codex / Gemini / Kimi session
    -> ArenaScript decision
    -> coordinator compiler/interpreter
    -> protocol-v2 action_command
    -> Java/Carpet action executor
    -> action_progress/action_result + observation
    -> next real provider turn or program completion
```

The runner may observe and record the path, but it must not inject an action result, bypass protocol validation, or install model source directly.

## Scenario matrix

The checked-in example matrix contains safe, bounded smoke scenarios. A matrix entry has this shape:

```json
{
  "id": "codex-chat-completion",
  "provider": "codex",
  "model": "gpt-5.6-sol",
  "reasoningEffort": "high",
  "serviceTier": "fast",
  "task": "Send exactly one chat message HEADLESS_CODEX_PASS, then finish the goal.",
  "timeoutMs": 180000,
  "assert": [
    { "type": "lifecycle", "state": "COMPLETED" },
    { "type": "chat", "message": "HEADLESS_CODEX_PASS" }
  ]
}
```

The normalized entry must contain a unique `id`, a supported provider, model, reasoning effort, service tier when applicable, nonblank task, a positive bounded timeout, and at least one assertion. Agent names and bridge identities are generated by the runner so repeated matrix entries cannot collide.

The command supports selecting one entry by ID or running all entries sequentially. Each entry gets a fresh server, world, coordinator, bridge secret, ports, trace directory, and generated agent name so one model cannot inherit another scenario's world or session. `--require-all` turns unavailable-provider skips into a matrix failure; without it, the report distinguishes `passed`, `failed`, and `skipped` entries.

## Provider profile validation

Before starting a scenario, the runner performs the provider-specific local preflight already required by the repository:

- Codex login status and model availability.
- Antigravity executable availability and catalog/model availability.
- Kimi executable/ACP availability and catalog/model availability.

The coordinator's live catalog and Java summon validation remain the final authority. If the exact tuple is rejected after startup, the scenario is reported as skipped or failed according to `--require-all`; the runner never substitutes a nearby model or reasoning level. The runner never reads provider credentials. Existing provider services inherit their normal local login state through the existing credential boundary, while the coordinator bridge secret is excluded from provider child environments.

## Real headless Fabric lifecycle

Each scenario uses a generated run directory under `runtime/headless-runs/<run-id>/<scenario-id>/` containing a copied dedicated server configuration and fresh world. The source server template is supplied explicitly or defaults to the repository's prepared headless server template. It must not reuse `run/world` or mutate an operator's normal installation.

The PowerShell wrapper:

1. Verifies Java 25, Node 22+, the built mod, Fabric server launcher, and the selected provider prerequisites.
2. Allocates free Minecraft, RCON, and coordinator bridge ports.
3. Starts Fabric with `nogui`, RCON enabled, and a private server log.
4. Waits for the server's `Done (` marker and RCON readiness.
5. Starts `dynamic-main.mjs` with the run's bridge secret and isolated trace paths.
6. Waits for authenticated bridge/catalog readiness.
7. Executes the runner scenario through RCON.
8. Stops the agent, coordinator, server, and all descendant provider processes in `finally` cleanup, even after timeout or assertion failure.

The wrapper must leave no listener on its allocated ports. A cleanup failure is a run failure, not a warning.

## Protocol and evidence capture

All coordinator-to-server and server-to-coordinator records are captured after the canonical protocol-v2 encoder/validator boundary. The coordinator bridge receives an optional audit callback that records every validated envelope before it is emitted or written to the socket; this callback is disabled for ordinary production launches. Each JSONL row includes the run ID, scenario ID, direction, timestamp, message type, agent ID, message ID, and normalized payload. Invalid envelopes fail the run immediately.

The existing public and private coordinator trace writers remain authoritative for lifecycle, planner, program, action, and timing events. The new provider-turn recorder adds bounded local records for the actual planner input and provider model output at the provider service boundary. The recorder must:

- preserve the exact text received from the selected provider up to the existing decision/output byte limits;
- include provider, model, reasoning effort, goal revision, attempt, retry status, and outcome/error code;
- redact credential-shaped keys and token text using the existing trace redaction utility;
- write full bounded content only to the run-private artifact, never to public traces;
- write a hash and bounded excerpt to the public run summary;
- never capture environment variables, process command lines containing credentials, or OAuth files.

The provider hook is observational. It cannot change the parsed decision, retry policy, provider session, or action scheduling.

## Assertions

The first assertion set is deliberately small and based on observable server evidence:

- `lifecycle`: `/codex status` reaches an expected terminal state (`COMPLETED`, `ERROR`, or `DEAD` as selected by the scenario).
- `chat`: the server log contains an exact agent chat message.
- `action`: a protocol/action trace contains an expected action type and optional bounded argument fields.
- `program`: coordinator trace contains `program_compiled`, `program_step`, and/or `program_finished` with the expected status.
- `rcon`: an explicitly configured read-only RCON command returns an expected bounded text match, for world-state checks such as a block or position.

Assertions are evaluated only after the agent has reached its terminal condition or the scenario timeout. A missing assertion is a failure with evidence paths, not an inferred pass.

## Reports and retention

Every matrix invocation produces a matrix report and one isolated artifact directory per scenario:

```text
runtime/headless-runs/<run-id>/
  matrix-manifest.json
  matrix-report.json
  <scenario-id>/
    manifest.json
    report.json
    protocol.jsonl
    provider-turns.private.jsonl
    coordinator.jsonl
    coordinator-private.jsonl
    server.log
```

`report.json` contains overall status, scenario statuses, exact profiles, elapsed durations, assertion results, skipped reasons, cleanup status, artifact paths, and hashes for the built mod. It does not contain credentials or unbounded raw logs. The run directory is ignored by Git and can be retained for debugging or removed by the runner's bounded retention option.

## Failure semantics

- Unsupported profile, missing login, unavailable executable, or unavailable catalog entry: `SKIPPED` unless `--require-all`, then `FAILED`.
- Provider startup, provider turn, bridge, parser, compiler, or action execution error: `FAILED` with the typed code and bounded diagnostics.
- Agent `ERROR`, `DEAD`, unexpected lifecycle state, stale revision, invalid protocol envelope, or assertion mismatch: `FAILED`.
- Timeout: cancel the goal, capture the final status and traces, clean up descendants, then `FAILED`.
- Successful terminal assertions and clean process teardown: `PASSED`.

The runner returns a nonzero process exit code for any failed scenario, a cleanup failure, or a required-but-skipped scenario. A matrix with only optional skips returns zero and clearly reports that no live provider scenario ran.

## Testing strategy

The feature is verified in layers:

1. Node unit tests cover matrix schema, provider/profile normalization, assertion evaluation, report redaction/bounds, RCON framing, and process-result classification.
2. A coordinator integration test verifies provider-turn recording through the real `AgentPlanner` hook without making an external provider call.
3. A real-provider command is opt-in and is documented with exact prerequisites. It runs at least one Codex scenario when Codex is authenticated and supports provider matrix expansion for Gemini and Kimi.
4. Existing `npm test`, Gradle `check`, `verifyCore`, and packaging tests remain unchanged and must continue to pass.
5. The final verification report includes real provider/model/settings, provider output artifact paths, protocol/action evidence, world assertions, final lifecycle state, and cleanup/port evidence.

## Implementation boundaries

The likely files are:

- `coordinator/src/headless-matrix.mjs`: manifest loading, normalization, scenario execution, assertions, and report model.
- `coordinator/src/headless-rcon.mjs`: bounded RCON client and command result normalization.
- `coordinator/src/provider-turn-recorder.mjs`: private/public provider-turn capture using existing redaction rules.
- `coordinator/src/protocol-v2.mjs` and `coordinator/src/dynamic-main.mjs`: optional validated-envelope audit injection for headless runs only.
- `coordinator/test/headless-matrix.test.mjs`, `coordinator/test/headless-rcon.test.mjs`, and `coordinator/test/provider-turn-recorder.test.mjs`: focused unit/integration tests.
- `coordinator/config/headless-provider-matrix.json`: checked-in example scenarios with no secrets.
- `scripts/run-headless-provider-matrix.ps1`: Windows Fabric/coordinator/process lifecycle wrapper.
- `README.md`: prerequisites, commands, artifact layout, and explicit real-provider/cost warning.
- `.gitignore`: ignore generated headless run artifacts if the existing `runtime/*` rule does not already cover the selected path.

No production command registration or client UI changes are required.
