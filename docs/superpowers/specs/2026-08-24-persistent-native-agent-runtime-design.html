Approved runtime design

Persistent native Minecraft agents

Make every active goal keep moving until Minecraft verifies completion or a real terminal event occurs. Recoverable provider, bridge, action, and coordinator failures must never silently strand an agent.

The shared root cause is architectural: no module owns the invariant that unfinished active work must always be live or scheduled to continue.

Core decision

Add one event-driven active-goal supervisor at the coordinator lifecycle seam. It owns continuation and recovery scheduling. A small lease timer catches missed events without turning normal operation into polling.

Retries scattered through individual catch blocks and a continuously polling watchdog were rejected because both duplicate lifecycle policy and leave more race conditions.

The active-goal invariant

For every current goal revision in STARTING, PLANNING, or ACTING, at least one continuation must exist:

  • a provider turn is queued or running;
  • a physical action is running;
  • completion verification is running;
  • a fresh observation is pending;
  • a recovery attempt is scheduled.

Every callback is fenced by agent ID, goal revision, and lifecycle generation. Recovery work is coalesced so one agent revision cannot create duplicate retries.

Native control and shared instructions

Codex agents use native Minecraft tools by default, including installations with preserved legacy configuration. Every agent gets the same static, read-only job and tool guidance while its conversation, goal, observations, provider state, and tools remain isolated.

Continuation flow

An observation starts or steers a native provider turn.
The model calls the smallest useful Minecraft action and receives its structured result.
If the turn ends while the goal is unfinished, the supervisor requests a fresh observation.
The next turn continues from current world state, including recovery from timeouts, blocked paths, missing drops, or changed terrain.
Only Minecraft's verifier may complete the goal.

Recovery policy

  • Recover provider disconnects, timeouts, rate limits, bridge loss, action timeouts, and blocked paths without producing terminal ERROR or PAUSED.
  • Retry from 250 ms with exponential backoff capped at 5 seconds.
  • Reset failure state after useful progress, a fresh observation, reconnection, or a successful provider turn.
  • Preserve explicit pause. Automatically resume interrupted active work after authenticated reconciliation.
  • End only on verified completion, explicit stop/removal/cancellation/replacement, unrecoverable death, a factually supported impossible result, or shutdown.

Logging and diagnostics

Expected bridge refusal is logged once, counted, and summarized on recovery. Unexpected errors retain structured diagnostics such as agent ID, goal revision, lifecycle generation, provider, active-work kind, stable error code, and stack.

Coordinator stdout and stderr rotate at a fixed size with bounded retained generations, preventing another hundreds-of-megabytes failure log.

Verification

The fault matrix covers legacy config migration, shared read-only instructions, zero-tool and one-action turns, provider failures, bridge reconnects, explicit pause, revision fencing, death and respawn, moved item drops, completion retries, terminal state alignment, orphan cleanup, and bounded logs.

The full coordinator, Java protocol, voice addon, and headless suites remain required. The final scenario must prove several sequential actions continue across multiple native turns while recoverable faults are injected between actions.

Scope and risks

Included

Codex Minecraft control, goal liveness, reconnect handling, process logging, and the shared instruction workspace.

Deliberately excluded

Agent-selection UI redesign, MCP, a shell CLI, non-Codex protocol redesign, and hidden chain-of-thought exposure.
