Implementation plan

One chosen brain. One reliable Minecraft body.

Reduce latency, stop false completion, and make 1 to 16 agents reliable without replacing, routing around, or silently assisting the provider, model, reasoning level, and service tier selected for each agent.

ArchitectureDecision locked
EvidenceMiniPC A/B and Desktop headless runs
Next stepImplement in nine verified tasks

Goal

The exact selected tuple { provider, model, reasoningEffort, serviceTier } is the agent's only brain. The universal body may observe, validate, pathfind, and execute, but it may not invent goals, tactics, speech, reactions, or completion.

What the brain owns

  • Goals, plans, tactics, priorities, and reactions.
  • What to say, when to say it, and whether to reply.
  • Persistent conditional behavior expressed as ArenaScript watchers.
  • The factual conditions that define completion.

What the body owns

  • Perception, exact physical inputs, navigation, and crafting mechanics.
  • Death, respawn, checkpoint restoration, DM, and voice delivery.
  • Urgent attention signals and pausing conflicting physical input.
  • Factual postcondition checks against the Minecraft world.

System boundary

Perception

Evidence behind the plan

MiniPC A/B result

The optimized build capped planning concurrency at four while the baseline used sixteen. At sixteen agents, scheduler p95 rose to roughly 7.5 seconds. Stone completion moved from 3.184 to 10.721 seconds and DM completion from 2.640 to 10.127 seconds. Memory improved modestly, but the fixed cap made the practical result worse.

Open MiniPC report

Desktop headless result

Minecraft was healthy at 1.6 ms average tick and 3.1 ms p99. The first visible action took 53 seconds. The agent later reported success without a wooden pickaxe in inventory. This places the main bottleneck in the provider and orchestration path, with a separate correctness failure in completion validation.

Risks and controls

Provider capacity differs

Adaptive scheduling can reduce avoidable queueing but cannot create provider throughput. Keep provider time separate and never route to another model.

Watchers can become accidental policy

Require brain attribution, explicit scope, bounded actions, cancellation, and no goal or speech creation inside the runtime.

False completion damages trust

Completion remains blocked until factual verification succeeds. Chat text and model confidence never count as proof.

Benchmark settings can distort results

Compare code with identical model and scheduler settings. Measure scheduler tuning in a separate sweep and retain raw run metadata.

Execution

  1. Create an isolated implementation worktree from the current optimized branch, preserving its validated fixes while replacing the scheduler regression and body-authored safety policy.
  2. Execute tasks in order because instrumentation and the single-brain boundary define the evidence required by later work.
  3. Use superpowers:subagent-driven-development for independent Java, coordinator, and benchmark ownership, with one integration owner to prevent collisions.
  4. For every task: write the failing test, confirm it fails for the intended reason, implement the smallest fix, run focused tests, then run the affected integration slice.
  5. Do not merge, deploy, replace a normal mod jar, or change a provider profile until the complete release matrix passes and Lucas approves the result.
